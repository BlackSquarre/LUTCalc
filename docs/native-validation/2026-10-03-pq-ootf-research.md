# 2026-10-03 PQ OOTF 公式冲突研究阻塞

## 结论

本轮没有把旧 JS 的“PQ OOTF”直接改写成 Swift 产品算法。旧实现与 BT.2100 的绝对 PQ/OOTF 参数语义没有形成可验证的一一对应关系，且旧分段在阈值处存在明显不连续；在没有独立规范参照前，继续实现会把历史行为误标成标准 HDR 变换。

## 来源

- 旧实现：`js/gamma.js` 中 `LUTGammaOOTFPQ`，源文件 SHA-256：`250017d8efe758f3555148ba9fcb923698add0ac7d9380fa290716eb98e0821e`。
- 标准入口：[ITU-R BT.2100](https://www.itu.int/rec/R-REC-BT.2100/en)。当前项目已有 `PQTransfer` 按 SMPTE ST 2084/BT.2100 处理绝对 PQ 编解码，但这不能自动证明旧 OOTF 的场景到显示映射。

## 旧实现最小复现

旧函数先令 `x = input / 100`，再按 `x > 0.0003024` 分段：

```text
x > 0.0003024: 1.099 * (59.5208 * x)^0.45 - 0.099
否则:          267.84 * x
结果: min(Lw / 100, x^2.4) * scale
```

用同一 Double 公式计算：

| `Lw` | 输入 | nits 输出 | normalized 输出 |
| ---: | ---: | ---: | ---: |
| 1000 | 0.18 | 5.704834098099198 | 0.000570483409809920 |
| 10000 | 0.18 | 5.704834098099198 | 0.000570483409809920 |
| 1000 | 100 | 1000 | 0.1 |
| 10000 | 100 | 9999.993723673924 | 0.999999372367392 |

分段阈值对应的输入约为 `0.03024`。在阈值两侧，nits 输出分别约为 `0.240047581924242` 和 `0.241822718722972`，存在约 `1.78e-3` 的跳变。这不是可直接放宽误差阈值或用插值隐藏的数值误差，而是旧公式本身的语义问题。

完整命令输出和 SHA-256 见[`artifacts/2026-10-03-pq-ootf-research`](artifacts/2026-10-03-pq-ootf-research)。

## 未决问题

1. `input` 的单位究竟是场景百分比、线性 IRE 还是其他旧内部单位。
2. `Lw` 的 `/100` 与 `scale=100/0.01` 是否属于旧 UI 的双重单位约定。
3. 旧分段阈值是否应保留为兼容身份，还是应按公开标准重建连续公式。
4. BT.2100 场景到显示 OOTF 的参考白、系统 gamma、峰值和黑位如何与该历史路径对应。

因此当前只保留 `PQTransfer` 的标准绝对 PQ 编解码和 HLG OOTF 已验收子集；PQ OOTF 继续标记为研究阻塞，不新增内置采样表、不读取 JavaScript，也不伪造完整 HDR 验收。
